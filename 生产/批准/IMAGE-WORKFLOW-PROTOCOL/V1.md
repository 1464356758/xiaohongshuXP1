# XHS-XP1｜图片工作流补充协议 V1

## 1. 协议身份
- protocol_id: IMAGE-WORKFLOW-PROTOCOL
- version: V1
- status: APPROVED_BY_R01
- applies_to: xiaohongshuXP1 / SYS-004 / CONTENT-*
- roles: R01, R08, R09, R10, R11, R12，以及后续需要实际像素的角色
- effective_scope: 图片文件传输、图片身份登记、像素审核输入
- architecture_change: false

## 2. 与 SYS-003 的兼容边界
本协议不得修改或绕过 SYS-003 已锁定的 state/phase、ASSET_IDENTITY_GATE、LOCK/Gate 权限或 R01 唯一控制面权限。

SYS-003 的 ASSET_IDENTITY_GATE 已明确支持 USER_FILE 与 GITHUB 两种资产传输方式。因此本协议只把常规最终图片的默认 transport 调整为 USER_FILE，不改变 gate 本身。

任何 CONTENT 进入 IMAGE_REVIEW 前，仍必须满足：
1. P1-P5 每个 ACTIVE 页面存在真实图片；
2. 每个 ACTIVE 页面存在非空、机器可验证的 identity；
3. identity 来源只能是实际字节 SHA-256、Git Blob+SHA-256，或平台不可变文件/附件 ID；
4. ASSET MANIFEST 必须存在非空 manifest_fingerprint；
5. 只有 R01 可以激活 manifest；
6. 只有 manifest 激活后，R01 才能创建 R10/R11/R12 IMAGE_REVIEW 并行组。

禁止仅凭文件名、聊天文字、视觉计划、prompt 或“图片已生成”的口头描述通过资产身份门禁。

## 3. 总原则
GitHub 是正式控制面和文字证据真源。

GitHub 继续承载：
- 当前进度与正式任务
- 文案、策划、视觉策划、逐页图片任务
- PRODUCT / SKU / PERSONA / CONTENT 等 LOCK
- ASSET MANIFEST 文字记录
- 审核结果、barrier、Gate、发布记录、数据记录

最终图片 P1-P5 默认不要求写入 GitHub 二进制。

最终图片默认由当前图片执行端实际生成，并以 USER_FILE 方式向后续需要实际像素的角色提供。

## 4. R08
R08 只负责视觉施工图和逐页图片任务包，不要求把最终图片写入 GitHub，也不以 GitHub 中是否存在 PNG/JPG 作为完成条件。

R08 必须让 R09 无需自行补设计即可执行。

## 5. R09
R09 负责实际生成 P1-P5。

默认输出方式：
- asset_transport: USER_FILE
- 不强制写入生产/产物/图片执行/ 下 PNG/JPG 二进制
- 必须返回实际生成的 P1-P5 图片给用户
- 必须建立 GitHub 中的 ASSET MANIFEST 与交付 JSON

R09 不得用 prompt、说明文件或路径占位代替实际图片。

若 R09 可直接取得生成图片的实际字节 SHA-256 或平台不可变附件 ID，则可直接登记 manifest。

若 R09 生成图片后无法取得机器可验证 identity：
- 不得 PASS；
- 返回 BLOCKED_ASSET_IDENTITY_UNVERIFIABLE；
- 明确要求用户把刚生成的 P1-P5 原文件重新上传到当前 R09 对话；
- 用户无需手算 SHA；
- R09 收到实际文件后自动计算/读取 identity，再建立 manifest。

R09 不得自行激活 manifest，不得创建 R10/R11/R12 任务，不得修改 state/phase/active pointer。

## 6. USER_FILE ASSET MANIFEST
manifest 仍写入 GitHub，并至少包含：
- asset_manifest_id
- manifest_revision
- content_id
- task_version / input_revision / revision_round
- page_id
- asset_id
- asset_revision
- fingerprint_type
- fingerprint
- sha256（如可获得）
- immutable_attachment_id（如适用）
- asset_ref
- asset_transport=USER_FILE
- status=ACTIVE
- persona_required
- product_required
- manifest_fingerprint

manifest_fingerprint 继续按 SYS-003 ASSET_IDENTITY_GATE 对 ACTIVE 页面 canonical identity 自动计算。

图片不在 GitHub，不等于图片没有正式身份。

## 7. R01
R01 不得假设 GitHub 中存在图片二进制。

R09 返回后：
1. R01 机械验证 manifest 与五页 identity；
2. ASSET_IDENTITY_GATE PASS 后激活 manifest；
3. 执行 IBC，再执行 IBR；
4. 创建 R10/R11/R12 独立正式 task 与 IMAGE_QA barrier；
5. 回复用户时明确告诉用户哪个角色需要上传哪些图片。

未激活 manifest 前，R10/R11/R12 不得启动。

## 8. 三审实际图片上传集合
默认最小集合：
- R10 商品图片核验：P1、P2、P5
- R11 人物一致性审核：P1、P3
- R12 图片终审：P1-P5 全部

如果正式 task 的 in-scope pages 更小，以 task 为准。

用户上传给审核角色的文件必须与 active manifest 中对应页为同一字节版本。审核角色应优先核对实际字节 SHA-256；不匹配则 STALE 或 BLOCKED_CONFLICT，不得审核另一个版本。

## 9. R10
必须看到实际 P1/P2/P5（或 task 指定页）像素后才可审核商品/SKU身份。
未收到实际图：BLOCKED_ASSET_MISSING 或 BLOCKED_INPUT_MISSING。
禁止仅凭 GitHub 路径或聊天描述 PASS。

## 10. R11
必须看到实际 P1/P3（或 task 指定人物页）像素后才可审核 PERSONA 一致性。
未收到实际图：BLOCKED_ASSET_MISSING 或 BLOCKED_INPUT_MISSING。
视觉策划正确不能替代人物像素审核。

## 11. R12
必须看到 P1-P5 当前 ACTIVE 实际像素后才能进行整组终审。
不得用 R10/R11 结论代替自身视觉终审。

## 12. 用户上传提示规则
凡下一角色需要实际图片，R01 必须在路由回复中明确写：
“下一步需要把以下图片手动上传给【角色】：……”。

用户只负责上传文件，不要求用户计算 SHA、fingerprint 或 manifest_fingerprint。

## 13. 图片命名
推荐用户本地文件名：
- CONTENT-001_P1_R1.png
- CONTENT-001_P2_R1.png
- CONTENT-001_P3_R1.png
- CONTENT-001_P4_R1.png
- CONTENT-001_P5_R1.png

实际身份以字节 fingerprint 为准，文件名不是身份凭证。

## 14. 图片返修
图片发生实际变化：
- 变化页 asset_revision +1；
- manifest_revision +1；
- 未变化页保持原 identity；
- 只使受影响审核证据 STALE；
- 不允许为了返修一页把无关页面全部推倒。

## 15. 发布前
R14 如需要看最终图片像素，由 R01 明确要求用户上传当前 CONTENT LOCK 绑定的最终页。
发布包仍必须绑定当前 active manifest 与 final copy fingerprint。

## 16. 当前暂不写死、后续可增补
以下内容留作后续版本补充，不影响 V1 生效：
- 不同客户端生成图片后可获得的 immutable attachment ID 具体格式
- USER_FILE 在各角色会话中的自动继承能力
- 发布前本地归档目录规范
- 最终整包 ZIP 的统一命名与归档周期
- 大批量多 CONTENT 并行时的用户上传交互优化

## 17. 核心执行口径
GitHub 管控制面和文字证据；最终图片默认走 USER_FILE。
实际像素审核必须看到实际文件。
USER_FILE 仍必须通过 SYS-003 ASSET_IDENTITY_GATE。
不得以“图片不进 GitHub”为理由绕过 manifest、fingerprint、barrier 或图片三审。
